# M5Stack CoreS3 NES エミュレータ

`core/` の NES コアを M5Stack CoreS3 (ESP32-S3) 上で動かす PlatformIO プロジェクト。
コントローラ入力は Grove 接続のユニット (ジョイスティック + 2ボタン) または
Mac 側からの UDP 送信。

## セットアップ

`pio` は `nix develop` または direnv 経由で入る前提。

```sh
cd m5stack
./scripts/fetch_rom.sh              # data/game.nes を取得
cp src/secrets.h.example src/secrets.h
$EDITOR src/secrets.h               # WIFI_SSID / WIFI_PASS を設定
pio run -t upload
```

`src/secrets.h` は `.gitignore` 済み。ROM (`*.nes`) もコミットされない。

## 起動シーケンス

1. microSD をマウントし、`/roms/` の `.nes` を走査してシリアルに一覧を出力
2. `Connecting to <SSID>...` を表示して WiFi 接続
3. 接続できたら自 IP を約 2 秒表示 (この IP を Mac 側ツールに渡す)
4. 埋め込み ROM をロード
5. SD に ROM が 1 本以上あれば ROM 選択メニューを表示、無ければそのままゲーム開始

WiFi に失敗してもゲームは起動する (Grove コントローラーは使用可、画面下部に `WiFi: failed` を表示)。
埋め込み ROM のロードに失敗した場合はエラー表示のまま停止する。

**SD カードが無くても従来どおり動く。** カード未挿入、マウント失敗、`/roms/` が空、
いずれの場合もメニューを出さずに埋め込み ROM で起動する。メニューは選ぶものが
実際にあるときだけ起動を待たせる。

## SD カードの ROM

FAT (FAT16 / FAT32) でフォーマットした microSD の `/roms/` に `.nes` を置く。
Mac で手動コピーするだけでよく、専用のツールや初期化手順は要らない
(`/roms/` が無ければ起動時に作られる)。

- 対応マッパーは **0 / 1 / 2 / 3 / 4 / 24 / 26 (VRC6)**。それ以外は選んでも
  `bad ROM` で弾かれる
- 1 本あたり **1MB (`ROM_MAX_SIZE`)** まで。ステージング用バッファの上限で、
  Web からの転送と同じ制限
- 一覧に載るのは **64 本 (`SD_ROM_MAX_FILES`)** まで、ファイル名は `.nes` を含めて
  **63 バイト**まで (UTF-8 のバイト数であって文字数ではない)。`.nes` で終わらない
  名前は拡張子を足した結果が 63 バイトに収まるよう切り詰められる。溢れた分は
  シリアルに警告を出して読み飛ばす
- 一覧は大文字小文字を無視した名前順。書き込み途中のファイルは `.nes.part` で
  置かれ、成功したときだけ最終名へ rename されるので、中断した書き込みが
  完成品と混ざることはない

カードは LCD と SPI バスを共有しているため、SD アクセスはすべて core 1 の
フレーム境界で行う (`config.h` の SD セクション参照)。SPI クロックは 25MHz で、
相性が出る個体は `SD_SPI_FREQ` を下げる。

I/O エラーを検知した場合は 1 度だけ自動で再マウントする (抜き差しからの復帰用)。
それでも駄目なら以降の操作がエラーを返し、そのつど再試行される。

## ROM 選択メニュー

先頭行が埋め込み ROM (`built-in`)、以降が SD 内の `.nes`。

| 操作 | 割り当て |
| --- | --- |
| 行をタップ | その行を選んで起動 |
| Grove の上下 / UDP パッドの上下 | カーソル移動 (長押しでオートリピート) |
| A / Start (BtnB) | カーソル行を起動 |
| BtnC 長押し | ゲーム中 → メニューを開く / メニュー中 → 何もせず復帰 (resume) |
| 頭を撫でる | (M5Stack 公式 StackChan の場合) ゲーム中 → メニューを開く |

- ゲーム中の BtnC 長押しが唯一のスタンドアロンな ROM 切り替え手段。以前ここに
  あった RESET は UDP type 2 から届くので、他に手段のないほうへ割り当て直した
- M5Stack 公式の StackChan ボディなら、頭頂部をなでなで (2 回ほど) しても
  メニューに戻れる。頭の 3 ゾーンをなぞった距離で判定するので、掌でぽんと
  触れただけでは反応しない。詳細は下の「頭を撫でる」を参照
- 起動に失敗しても**メニューに留まる**。直前のカセットはロードされたままなので、
  フッタに理由 (`not found` / `bad ROM` / `no SD card` など) を出して選び直せる
- メニューを開くたびにカードを再走査する。UDP でファイルが増えていたり、
  カードを差し替えていても最新の一覧が出る
- メニュー表示中も UDP の type 4 / type 5 は動く。ブラウザから「起動する」
  ROM を送ればそのままゲームに入り、保存のみの転送や削除・リネームなら
  一覧を描き直す

## Web UI からの SD 管理

`just serve` して `http://localhost:8000/?device=<CoreS3 の IP>` を開くと、
`?device=` を付けたときだけ SD パネルが出る。

- **一覧・容量** — ファイル名とサイズ、カードの空き / 総容量を表示。「再読込」で更新
- **起動** — その ROM を実機でロードして開始 (type 5 LOAD)
- **リネーム / 削除** — type 5 RENAME / DELETE。リネーム先が既にあるときは
  `already exists` で失敗する (上書きの確認はユーザーに聞ける UI 側の仕事なので、
  ファームは黙って潰さない)
- **ローカル ROM の SD 保存** — ROM 送信時に「SD カードにも保存」を選ぶと、
  転送した ROM をそのままカードにも書く。「保存のみ (起動しない)」を併用すれば
  実行中のゲームを止めずにライブラリだけ増やせる
- **URL 指定ダウンロード** — URL を入れると `tools/serve_web.py` が代理で取得し、
  実機へ転送する。実機に TLS スタックが無いので、ダウンロードは PC 側で行う

実機は SD リクエストを **同時に 1 件しか**受け付けず、残りには `busy` を返す。
そのためパネルは 1 コマンドの間ボタンを丸ごと無効化する。

ファイル名は実機側で必ずサニタイズされる。ディレクトリ部分は捨てられて
basename だけが残り、`A-Za-z0-9._-` 以外は `_` に置換、拡張子は `.nes` に
正規化される。サニタイズ結果が元と違う名前は `bad name` で拒否するので、
勝手に化けた名前で保存されることはない。

## Grove コントローラー

UDP がなくても、Grove 接続のユニットだけでスタンドアロンに遊べる。
UDP 入力とは OR 合成されるので、併用しても衝突しない (パッド1のみ)。

| 接続先 | ユニット | 割り当て |
| --- | --- | --- |
| PORT.B (黒) | Joystick Unit (U024) / Joystick2 Unit (U024-C) | スティック=十字キー、押し込み=Start |
| PORT.C (青) | Dual Button Unit (U025) | 青=B、赤=A |
| 画面下タッチゾーン | (本体) | 左=Select、中央=Start、右長押し=メニューを開く |

ポート割り当てはスタックチャン (K151) の背面ポート向け。ポートの色は用途の
目安でしかなく、実体はただの GPIO なので、外部 I2C バスを PORT.B のピン
(SDA=G9 / SCL=G8) に張り替えてジョイスティックを、PORT.C (G17/G18) を
GPIO 入力にして 2 ボタンを読んでいる。別のポートに変えたいときは
`src/config.h` の `JOY_I2C_*` / `DUAL_BTN_PIN_*` を書き換える
(PORT.A = G2/G1, PORT.B = G9/G8, PORT.C = G17/G18)。

- ジョイスティックは起動時に I2C アドレスで自動判別する (Joystick2=0x63 → 旧 Joystick=0x52 の順)。
  未接続でも約 1 秒ごとに再プローブするので、あとから挿しても認識する。
  検出結果はシリアルに `GROVE: ...` と出る。
- 上下左右が逆に感じる個体は `config.h` の `JOY_INVERT_X` / `JOY_INVERT_Y` を反転する。
  デッドゾーンは `JOY_DEADZONE`。
- ポーリングは Core 0 の専用タスク (8ms 周期) で行い、I2C の遅延がフレームループに
  乗らないようにしている。ジョイスティックを抜くと読み取り失敗を検知して
  ボタンを離した状態に戻り、再プローブに移行する。

## 頭を撫でる (M5Stack 公式 StackChan)

M5Stack 公式の StackChan ボディには頭頂部に静電容量式のタッチセンサー (Si12T) が
入っていて、頭を撫でる (なでなで) とゲーム中でも ROM 選択メニューに戻る。
判定は**撫でた距離**: 隣のゾーンに新しく触れたとき、および前のゾーンが離れて
隣が残ったとき (指がまたがったまま滑る動き) に 1 ずつ伸び、自然なひと撫でが
およそ 2 になる。`HEAD_TOUCH_TRAVEL_TO_MENU` (4 = ふた撫でぶん) に達したら開く。
向きは問わず、指を離さない連続のゴシゴシも、離しながらの複数ストロークも合算
される。動きが `HEAD_TOUCH_TRAVEL_RESET_MS` (1 秒) 途絶えると数え直し — 抱え
上げたときなどの偶発的な一触れ (片道 = 2) では開かない距離設定にしてある。

- センサーは M-Bus 経由で CoreS3 の**内部** I2C (SDA=G12 / SCL=G11) にアドレス
  `0x68` で載っている。Grove の外部 I2C とは別バスなので、ジョイスティックと
  併用しても衝突しない
- 起動時にプローブし、結果をシリアルに出す (`HEAD: si12t detected` /
  `HEAD: not found`)。公式ボディでない個体では `not found` になるだけで、
  起動やそれ以外の操作には影響しない
- 単発のタップ・掌で 3 ゾーンを同時に覆う・指を置いたまま止める・離れた場所に
  置き直す、では距離は伸びない (0〜1 止まり)。発火したら距離は 0 に戻り、
  続けて撫でればまた開く
- ポーリングはゲーム中のみ `HEAD_TOUCH_POLL_MS` (16ms) 周期で、メニュー表示中は
  走らない。読むのは OUTPUT1 レジスタ 1 バイトだけなのでフレーム予算への影響は
  無視できる
- ドライバとジェスチャー判定は M5Stack 公式 BSP
  ([m5stack/StackChan-BSP](https://github.com/m5stack/StackChan-BSP), MIT License)
  から移植した。詳細は `src/head_touch.cpp` のヘッダコメント

## Mac 側ツール

```sh
uv run tools/procon_udp.py --host <CoreS3 の IP>
```

Switch Pro Controller の入力を UDP で送信する。
`uv` は `nix develop` で入り、依存 (pygame) はスクリプト内の
PEP 723 メタデータから uv が解決する。pip install は不要。

## UDP プロトコル

ポート 5555。オフセット 3 が **type** で、パケット種別を表す。
旧クライアントはここを `reserved = 0` として送っていたため、
type 0 (パッド) は従来のパケットとバイト単位で互換。

### type 0: パッド (8 バイト)

| offset | 内容 |
| --- | --- |
| 0-1 | magic `'N'`, `'P'` |
| 2 | version = 1 |
| 3 | type = 0 |
| 4-5 | seq (uint16 LE, 現状未使用) |
| 6 | pad1 ボタンビット |
| 7 | pad2 ボタンビット |

ボタンビット: `bit0:A 1:B 2:Select 3:Start 4:Up 5:Down 6:Left 7:Right`

500 ms 以上パケットが途絶えると両パッドを離した状態に戻す。

### type 1: カセット端子状態 (14 バイト)

| offset | 内容 |
| --- | --- |
| 0-1 | magic `'N'`, `'P'` |
| 2 | version = 1 |
| 3 | type = 1 |
| 4-5 | seq (uint16 LE) |
| 6-13 | pin mask (uint64 LE) |

mask の **bit(n-1) = ピン n が導通**。60 本すべて 1 なら正常に挿さった状態。
変化したときだけコアに適用し、そのつどシリアルへ `PINS: %016llx` を出力する。

**端子状態はパッドと違いタイムアウトしない。** 接触不良は物理的な状態であり、
送信側が止まっても勝手に直るものではないため。復帰はブラウザの「まっすぐ挿す」
(= 全ビット 1 のマスク送信) で明示的に行う。

### type 2: コンソール制御 (8 バイト)

| offset | 内容 |
| --- | --- |
| 0-1 | magic `'N'`, `'P'` |
| 2 | version = 1 |
| 3 | type = 2 |
| 4-5 | seq (uint16 LE) |
| 6 | cmd (bit0 = RESET, bit1 = 音量設定, bit2 = ROM 選択メニューを開く) |
| 7 | 音量 0-255 (bit1 のとき有効) |

RESET は実機の RESET ボタンと同じ意味論で、ワーク RAM は保持したまま
リセットベクタから起動し直す。シリアルへ `RESET: console reset` を出力する。

音量は Web 設定ダイアログのマスターボリュームをミラーしたもの。
Web の 1.0 が `SPEAKER_VOLUME_BASE` (=128) に対応し、スライダーの 0..1.5 は
0..192 に写る。ミュート中は 0。適用時にシリアルへ `VOL: <n>` を出力する。
一度も受信していない間は `src/config.h` の `SPEAKER_VOLUME` のまま。
M5Unified は出力タスクの DMA ブロックごとに音量を読み直すため、
`setVolume()` は再生中のストリームにも即座に効く。

CPU バス系のピンを抜くとエミュレート中のプログラムが暴走することがあり、
**端子を戻すだけでは復帰しない** (リセットベクタを読み直す必要がある)。
そのためブラウザの「まっすぐ挿す」は、ピンマスク送信の直後にこの RESET も送る。

### type 3: デバッグスナップショット要求 (8 バイト)

| offset | 内容 |
| --- | --- |
| 0-1 | magic `'N'`, `'P'` |
| 2 | version = 1 |
| 3 | type = 3 |
| 4-5 | seq (uint16 LE) |
| 6 | flags (bit0 = APU 波形も要求) |
| 7 | 予約 (0) |

デバイスはフレーム境界でスナップショットを作り、**送信元へ複数のデータグラムに
分割して**返す (波形なし 2 パート / 波形あり 3 パート)。MTU を超えるため、
IP フラグメンテーションに頼ると断片が1つ落ちただけで全体を失う。分割は自前で行い、
パート数は応答ヘッダの nparts が自己記述する。

応答パケット: `'N','D' | version | part | nparts | seq エコー u16 | payload`

スナップショット本体 (2134 バイト):

| offset | サイズ | 内容 |
| --- | --- | --- |
| 0 | 12 | CPU レジスタ (Web 版 `nes_cpu_regs` と同レイアウト) |
| 12 | 24 | `apuRegShadow` ($4000-$4017 の最後の書き込み値) |
| 36 | 2 | PC (冗長。コード窓とセットで意味を持つため) |
| 38 | 48 | PC 近傍のコード窓 (逆アセンブラが辿る最大長) |
| 86 | 2048 | ワーク RAM |
| 2134 | 1680 | APU 波形 (flags bit0 のときのみ) |

読み取りは副作用なし。$2000-$401F は 0 として返す ($2002 を読むと vblank が
クリアされる等、観測が対象を変えてしまうため)。

波形は 6 行 × 280 サンプルの uint8 (P1, P2, TRI, NOI, DMC, MIX)。280 は
スコープのキャンバス幅で、ブラウザ側の `drawWaves` と同じ最近傍サンプル選択で
デバイス側が間引いてから送る (表示しない分を運ばないため)。MIX だけは float
なので `min(1, mix*2)` — `drawWaves` の表示スケールそのもの — を通して uint8
に量子化する。

波形要求を受けると **2 秒間だけ** APU の per-sample キャプチャが有効になり、
要求が途絶えると自動的に切れる (シリアルに `DBG: wave capture on/off`)。
見ていない間の実機コストを per-sample 1 分岐に抑えるための仕組み。

### type 4: ROM 転送

BEGIN / DATA* / END の 3 段でカセットイメージを送る (詳細は `src/config.h`)。
フラグで挙動が変わる。

| フラグ | 意味 |
| --- | --- |
| `ROM_FLAG_SWAP` (bit0) | CPU をリセットせずに差し替える (Web 版の `nes_swap_rom` と同じ) |
| `ROM_FLAG_SAVE_SD` (bit1) | 併せて SD にも保存する。BEGIN 末尾のファイル名が要る。保存に失敗したときはロードも行わない |
| `ROM_FLAG_NO_LOAD` (bit2) | ロードせず保存だけ行う (実行中のゲームを止めない) |

ファイル名付き BEGIN は**長さで判別**する。旧クライアントはちょうど
`UDP_ROM_BEGIN_SIZE` バイトを送るので、それより長ければ新形式と一意に決まる
(フラグで判別しようとすると、旧ファームが予約ビットを取っておく必要があった)。

`ROM_FLAG_SAVE_SD` を付けた転送で**保存が失敗したときはロードも行わない**。
「カードに置いて起動する」という要求の後半だけを叶えると、遊んでいたゲームを
止めた上にカードにも残らないので、再起動するとどちらも失われるため。失敗の
理由は下の保存イベントで返る。

SD 保存の結果は END の ACK とは**別のデータグラム**で返る。ACK は CRC が
通った時点で UDP タスクから即返すのに対し、カードへの書き込みは後で core 1 の
フレーム境界で走るため、そこまで ACK を待たせると 1-2 秒の書き込みの間
転送が開きっぱなしになる。

### type 5: SD カード操作

LIST / LOAD / DELETE / RENAME の 4 つ。type 4 と分けてあるのは、type 4 が
独自のセッション状態機械を持つバルク転送なのに対し、こちらは単発の
リクエスト / リプライだからで、同居させると無関係な ROM 転送の途中で
LIST が `busy` になってしまう。

リクエストは UDP タスクがラッチするだけで、実際の処理は必ず core 1 の
フレーム境界で行う (SPI バスを LCD と共有しているため)。同時に処理するのは
1 件だけで、保留中に届いた 2 件目には即座に `busy` を返す。

LIST の応答は必要なだけのデータグラムに分割され、各パートが `part` / `nparts` と
カードの容量を自己記述する (パート 0 を落としても再送で容量が拾えるように、
容量は全パートに載せる)。ROM が 0 本のカードも `count=0` のパートを 1 つ返すので、
「マウント済みで空」と「応答なし」は区別できる。

magic / version が一致しないパケットは破棄する。

## ブラウザから実機の内部状態を見る

ミラーモード中は DEBUG パネルの表示元を Local / Stack-chan で切り替えられる。
Stack-chan 側を選ぶと CPU レジスタ・逆アセンブル・APU レジスタ・WRAM ダンプが
実機の値になる (5Hz 更新)。

APU 波形スコープも実機の値を表示する。スナップショットに含まれないパターン
テーブルを使う CHR ビューアだけはローカルのままグレーアウトする。
WRAM はリモート時は読み取り専用 (ダブルクリック編集は無効)。

逆アセンブルは PC 近傍 48 バイトしか持たないため、窓の外は `??` と表示される。

実機側のコストは実測で、波形なしの 5Hz ポーリングが **-0.03fps (-0.1%)**、
波形ありでも **33.5 -> 32.7fps**。ポーリングしなければゼロ。

## ブラウザから端子をいじる

Web 版のカセット端子 UI を実機にミラーできる。サイコロ (接触不良の判定) は
ブラウザ側で振り、その結果を実機へ送るので、画面とパネルが同じカセットを映す。

```sh
just serve                       # web/ を配信しつつ UDP 中継も行う
# ブラウザで http://localhost:8000/?device=<CoreS3 の IP>
```

`?device=` は `localStorage` に保存されるので次回以降は省略できる
(クエリを付けた場合はそちらが優先)。ブラウザは UDP を送れないため、
同一オリジンの `POST /api/pins` を `tools/serve_web.py` が type 1 パケットへ
中継する。中継サーバーは 127.0.0.1 のみで待ち受ける。

## タスク構成

- **Core 1** (Arduino `loop()`) — エミュレーション + 音声 + 描画
- **Core 0** (`udp` タスク) — `recvfrom` でブロックし、ボタン状態の更新のみ行う
- **Core 0** (`grove` タスク) — 8ms 周期で Grove ユニットをポーリングし、ボタンビットを公開する

## 既知の制約

- 表示は約 30fps 程度に留まる見込み (エミュレーション自体は 60fps を目指してペーシング)
- WiFi の SSID / パスワードはコンパイル時に埋め込む (実行時設定 UI はなし)
- 描画は 256x240 等倍・x=32 で中央配置 (パネルは 320x240)
- `pushImageDMA` の転送は描画しないフレームの裏で走らせている。フレームバッファは
  内部 SRAM に 1 枚しか置けないため、次に描画するフレームの直前で転送完了を待つ
- RGB565 はコアのパレット LUT 側でバイトスワップ済み (`DISPLAY_SWAP_BYTES = false`)。
  ドライバ側でスワップさせるとラインごとにバウンスバッファを経由し、
  ゼロコピー DMA ができなくなるため
- CPU バス系のピン (2-13, 32-44) を抜いた場合、CPU はオープンバスを読む。
  読む瞬間のバス状態に依存するため、Web 版と実機で挙動が一致するとは限らない
  (PPU 系ピンは決定的で、両者ビット単位で一致する)

## 設定

`src/config.h` に UDP ポート、音量、`PERF_LOG`、バイトスワップなどの定数がある。
`PERF_LOG` を有効にすると 1 秒ごとに fps と emulation / push の平均 µs をシリアルに出力する。
